# configHash 少了两个字段 —— 而唯一能看见它的那个 runner 早就红了

> Sepolia · factory v0.33.0 `0x2A5cf40c24B8D27B8A039DE2b628fb4C9C66dAb9` · 2026-09-06
>
> **本文第一版有五条声称没有读数支撑，由评审逐条打回。** 现在每一条都跟着它的取数方式；
> 打回的那几条原样保留在下面「被打回的五条」里，因为它们是同一类错误的现场。

## 症状与真因不是同一件事

`createaccount-relay-passkey-e2e` 红在 `InvalidOwnerSignature()`。**这句话读起来是密钥问题，
实际是编码问题。**

`AAStarAirAccountFactoryV7._getConfigHash` 在 airaccount-contract **#161** 里从 8 个字段
变成 10（`+tier1Limit, +tier2Limit`，为的是让 native-ETH tier 档位不能被抢跑改掉）。
SDK 侧的 `InitConfig` **类型**在 `e322da1f`（2026-08-18, #326）跟上了 10 字段，
`createAccount` 传的 struct 也跟上了 —— **而复刻哈希的 `configHashFromInitConfig` 停在 8**。

**这个缺口存在于多少个已发布版本？一个。** 取数方式：

```
$ git log --format='%h %ad' --date=short -S 'tier1Limit: bigint' -- packages/core/src/actions/airAccount.ts
e322da1f 2026-08-18
c69fb5e1 2026-06-15                     ← 两个，不是一个

$ git show e322da1f -- packages/core/src/actions/airAccount.ts | grep '^+.*tier1Limit'
+    tier1Limit: bigint;                 ← 这个才是 InitConfig 那次

$ for t in $(git tag --list 'v0.*' --sort=creatordate); do
    git merge-base --is-ancestor e322da1f "$t" 2>/dev/null && echo -n "$t "; done
v0.45.0 v0.46.0-rc.1 v0.46.0-rc.2
```

即 **`v0.45.0` 一个正式版**，外加本轮的两个 rc tag。（第一版写「红了四个版本」，是没量的。）

> **第二行是评审补的，而它改的是量具不是结论。** `-S 'tier1Limit: bigint'` 是个**松量具**：
> 这个字符串在 `airAccount.ts` 里出现两次（`TokenConfig` 一次、`InitConfig` 一次），
> 所以 `-S` 命中两个 commit。`git log -L` 同样返回两个、并不判别。
> 真正分开它们的是 `git show <sha> -- <file> | grep '^+.*tier1Limit'`。
> 结论没变 —— 但一个**恰好只有一个候选落在 tag 祖先里**的松量具，和一个精确量具，
> 在输出上完全同形。

## 链上读数

### 判据一：零值 config（relay runner 用的那份）

| 口径 | 值 |
|---|---|
| 链上 `getConfigHash(config)` | `0x05ca2a0caa5c066a9c487b5e4ff62bcfe5ef35fec668304997d1e476097f249a` |
| SDK 复刻（8 字段，修前） | `0x01ed5cc0af69ede3e2b503b0a7d9d39099d310ccb44aa7794565dfc5355fa6e2` ❌ |
| 手算 10 字段（`+tier1/tier2`） | `0x05ca2a0caa5c066a9c487b5e4ff62bcfe5ef35fec668304997d1e476097f249a` ✅ |

**这份 config 的 `tier1Limit == tier2Limit == 0`。** 它能证明两个字段**在**原像里，
证明不了它们的**先后** —— 交换两个零不改变任何字节。所以需要第二份。

### 判据二：12 个叶子槽位全部互不相同的 config（block 11644989）

判据二的**第一版只钉住了 12 个槽位里的 7 个** —— `guardianP256X/Y` 全零、`initialTokens`
为空。评审用两条存活的变异把代价量了出来：

```
D  对调 guardianP256X / guardianP256Y            ->  5 passed  （存活）
E  TokenConfig 分量改成 (uint256,uint128,uint128) ->  5 passed  （存活）
正对照  对调 dailyLimit / minDailyLimit（值不同）  ->  2 failed  （量具是活的）
```

**正对照是承重的那行**：没有它，两个 `5 passed` 分不开「这个槽位没被钉住」和「变异根本没落地」。

这就是本次重写要消灭的形状**在另外五个槽位上的残留** —— 我给 tier 两个字段修好了
「交换两个零是 no-op」，却把同一件事原样留在了别处。

现在的向量：P-256 guardian `x ≠ y` 且均非零、一条 `initialTokens` 且其 `TokenConfig`
三分量互不相同、`dailyLimit ≠ minDailyLimit`、`tier1Limit = 2**128`、`tier2Limit = 7`。

#### 而「三分量互不相同」必要但不充分 —— E 第一次没死

补完向量后 **D 转红了，E 仍然 5 passed**。原因不是向量还有缺口，是 ABI 编码的性质：
静态 tuple 的每个分量各占一个 32 字节的字，所以对任何 `uint128` 装得下的值，
`(uint128,uint128,uint256)` 与 `(uint256,uint128,uint128)` **编码出逐字节相同的输出**。
E 是一条**等价变异** —— `verification.md` §1 记的第二类成因，而它和「测试是瞎的」表现完全相同。

**没有任何小值向量能钉住这几个宽度。** 钉住它们的是量级：声明为 `uint256` 的那个分量
带上 `2**128`，`uint128` 编码无法表示，变异于是抛错而不是给出相同字节。
和 mutation B 靠 `tier1Limit = 2**128` 是同一个道理。

> 写成通则，因为它不止于本文件：
> **要钉住一个字段的类型，需要一个错误类型装不下的值；要钉住它的位置，需要一个别的字段没有的值。**
> 这是两个不同的要求，一条向量必须逐字段同时满足。

`TokenConfig.dailyLimit` 改成 `2**128` 之后，D 与 E 都转红。

完整可重跑命令（`RPC_URL` **带引号** —— 见下）：

## 为什么之前的测试挡不住

原测试三条，只有一条碰 configHash：**「deterministic + 32 bytes」**。
它在 8 字段和 10 字段上都通过 —— *确定性是 keccak 的性质，不是「哈希了正确原像」的性质*。

而「digest changes if ANY consensus field changes」那条只变动了九个字段里的五个。
**「ANY」是一句关于集合的声称，抽样不构成它。** 现在逐字段各一行，九个全覆盖。

文件头原来那句「The bytes are CROSS-CHECKED on-chain by `createaccount-relay-passkey-e2e.ts`」
写的时候是真的，之后**悄悄变成了假的**：那个 runner 一直红着。

## 那条「可重跑」的命令，第二次没能兑现自己

上一轮的阻塞 ④ 是「命令把实参省成了 `...`」。补全实参之后，评审把它照抄进 shell：

```
$ bash -c 'RPC_URL=<sepolia-rpc> echo HELLO'
bash: sepolia-rpc: No such file or directory      ← 命令根本没执行
$ bash -c 'RPC_URL="https://example" echo HELLO'
HELLO                                              ← 对照
```

**未加引号的 `<` 是输入重定向。** 它落在**和阻塞 ④ 完全同一个位置** ——
「re-run the command, not the memory of it」这句自我要求，在它正下方那条命令上，
连续两轮都没有真正成立。

现已加引号，并且这次的验证方式换了：**把头注里那段命令用 `sed` 原样抽出来、灌进 `bash` 跑**，
输出与文件里 pin 的两个值逐字相同。一条关于可重跑性的承诺，只值它在 shell 里被粘贴一次所证明的东西。

## 变异读数（五条都实跑）

```
A  对调 tier1Limit / tier2Limit              → 2 failed   （死在两条实测向量上）
B  tier uint256 → uint128                    → 5 failed   （encodeAbiParameters 对 2**128 抛错）
C  改回 8 字段                                → 4 failed   （幸存：`is pure`，本就恒真）
D  对调 guardianP256X / guardianP256Y        → 2 failed   （旧向量下曾 5 passed 存活）
E  TokenConfig → (uint256,uint128,uint128)   → 5 failed   （旧向量下曾 5 passed；且补完
                                                「三分量互不相同」后仍存活——它是等价变异，
                                                直到 uint256 那格装上 2**128）
```

**A 顺带打了我自己一巴掌。** 我原来给那条不等式测试起的标题是
「present, **in this order**, at this width」—— 而变异 A 下它**照样绿**。
不等式只能显示两个输入哈希不同，**永远不能显示各自落在哪个槽位**。
顺序和宽度是由实测向量钉住的，不是由那几条不等式。标题已改成
「neither #161 tier field is dead」，并把这一点写进注释。
