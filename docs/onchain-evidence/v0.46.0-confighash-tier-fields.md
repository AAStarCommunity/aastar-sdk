# configHash 少了两个字段 —— 而唯一能看见它的那个 runner 早就红了

> Sepolia · factory v0.33.0 `0x2A5cf40c24B8D27B8A039DE2b628fb4C9C66dAb9` · 2026-09-06

## 症状与真因不是同一件事

`createaccount-relay-passkey-e2e` 红在 `InvalidOwnerSignature()`。**这句话读起来是密钥问题，
实际是编码问题** —— 这正是它红了四个版本没人追下去的原因。

`AAStarAirAccountFactoryV7._getConfigHash` 在 airaccount-contract **#161**（v0.29.0）里从 8 个字段
变成 10 个（`+tier1Limit, +tier2Limit`，为的是让 native-ETH tier 档位不能被抢跑改掉）。
`createAccount` 传的 struct 当时同步成了 10 字段，**而 SDK 里那份复刻 `configHashFromInitConfig`
停在 8**。configHash 错 → CREATE_ACCOUNT digest 错 → `ecrecover != owner`。

## 为什么之前的测试挡不住

原测试三条，只有一条碰 configHash：**「deterministic + 32 bytes」**。
它在 8 字段和 10 字段上都通过 —— *确定性是 keccak 的性质，不是「哈希了正确原像」的性质*。
而「digest changes if ANY consensus field changes」那条从未变动 `tier1Limit`/`tier2Limit`，
所以「ANY」是一句测试没有兑现的话。

文件头原来那句「The bytes are CROSS-CHECKED on-chain by `createaccount-relay-passkey-e2e.ts`」
写的时候是真的，之后**悄悄变成了假的**：那个 runner 一直红着。
一条声称自己被交叉验证过的注释，和一条真的被验证过的性质，读起来一模一样。
