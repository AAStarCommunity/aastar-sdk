## 症状与真因不是同一件事

`createaccount-relay-passkey-e2e` 红在 `InvalidOwnerSignature()`。**这句话读起来是密钥问题，
实际是编码问题。**

`AAStarAirAccountFactoryV7._getConfigHash` 在 airaccount-contract **#161** 里从 8 个字段
变成 10（`+tier1Limit, +tier2Limit`，为的是让 native-ETH tier 档位不能被抢跑改掉）。
SDK 侧的 `InitConfig` **类型**在 `e322da1f`（2026-08-18, #326）跟上了 10 字段，
`createAccount` 传的 struct 也跟上了 —— **而复刻哈希的 `configHashFromInitConfig` 停在 8**。

**这个缺口存在于多少个已发布版本？一个。** 取数方式：

```
$ git log -1 --format='%h %ad' --date=short -S 'tier1Limit: bigint' -- packages/core/src/actions/airAccount.ts
e322da1f 2026-08-18

$ for t in $(git tag --list 'v0.*' --sort=creatordate); do
    git merge-base --is-ancestor e322da1f "$t" 2>/dev/null && echo -n "$t "; done
v0.45.0 v0.46.0-rc.1 v0.46.0-rc.2
```

即 **`v0.45.0` 一个正式版**，外加本轮的两个 rc tag。（第一版写「红了四个版本」，是没量的。）

## 为什么之前的测试挡不住

原测试三条，只有一条碰 configHash：**「deterministic + 32 bytes」**。
它在 8 字段和 10 字段上都通过 —— *确定性是 keccak 的性质，不是「哈希了正确原像」的性质*。

而「digest changes if ANY consensus field changes」那条只变动了九个字段里的五个。
**「ANY」是一句关于集合的声称，抽样不构成它。** 现在逐字段各一行，九个全覆盖。

文件头原来那句「The bytes are CROSS-CHECKED on-chain by `createaccount-relay-passkey-e2e.ts`」
写的时候是真的，之后**悄悄变成了假的**：那个 runner 一直红着。

## 变异读数（三条都实跑）

```
A  对调 tier1Limit / tier2Limit   → 2 failed / 3 passed   （死在两条实测向量上）
B  uint256 → uint128              → 5 failed / 0 passed   （encodeAbiParameters 对 2**128 抛错）
C  改回 8 字段                     → 4 failed / 1 passed   （幸存：`is pure`，本就恒真）
```

**A 顺带打了我自己一巴掌。** 我原来给那条不等式测试起的标题是
「present, **in this order**, at this width」—— 而变异 A 下它**照样绿**。
不等式只能显示两个输入哈希不同，**永远不能显示各自落在哪个槽位**。
顺序和宽度是由实测向量钉住的，不是由那几条不等式。标题已改成
「neither #161 tier field is dead」，并把这一点写进注释。
