# verification — 门禁与读数的实践

> 「一次检查什么时候才真的检查了东西」。这些不是原则，是 2026-09-04 夜 #339–#360 那一轮里
> **每一条都由一次失败换来**的判据。每条都标了出处 PR，因为一条没有出处的实践规则，
> 和它要防的那种「只活在某人记忆里的事实」是同一个东西。
>
> 读法：动手改一道门禁、或写一条断言之前，扫一遍第 1 节和第 5 节。

---

## 1. 绿不算数，除非它能红

一条从没红过的断言，和一条恒真的断言，在输出上完全一样。

- **每条新断言都要变异一次**，且变异要针对**被测对象**，不是断言本身。
- **变异的读数要连变异写法一起报**。「3 红」不带变异内容，下一个人无法判断它红得对不对。
- **红也要归因**（FU-30，#339）。因超时而红和因断言而红，在 `× test name` 那一行上长得一模一样。
  凡 spawn 子进程的测试都给显式 timeout；判「变异见红」时确认红的原因指向被测对象。
- **变异是否生效，本身是一格读数，不是一句 print**（#352 review）。
  变异后重测被测量的那个数（如 `countCases` 3→2），而不是打印一句「已应用」。
  布尔的「那串还在不在」在多处出现时无意义 —— **计数才有意义**。

### 一条变异没红，有三种成因，只有读代码能分开

| 成因 | 例 |
|---|---|
| 测试是瞎的 | 事件排序规则从没被测过（#347 变异 C） |
| 改动没造成差别（**等价变异**） | 两个 `bytes32` 的 `abi.encode` 与拼接字节相同（#347 变异 A） |
| **链上/环境此刻造不出这个区别** | 集合从没变过 ⇒ 三个 epoch 快照根与 `runningRoot` 相等（#347 review） |

第三类最难认，因为它和第一类的表现完全相同。认出它之后**再往外走一步**：
那句「此刻造不出这个区别」描述的是一个事实 —— **这个事实还让哪些别的检验也失效了？**
（#347 里同一个事实同时废掉了排序检验和冻结根检验，我只接住了一个。）

### 一条跟进项可以靠「把规则写下来」被合法关掉，而规则点名的代码原封不动

（#363 在清 FU-46 时实测发现）FU-30 的正文是两半：**「红也要归因」这条认识** +
**「凡 spawn 子进程的测试都给显式 timeout」这个动作**。#360 把前一半写进了本节，
`followups.sh done FU-30 --pr 360` 于是成立。后一半的对象 `scripts/security-scan.test.ts`，
在那之后是 **14 个 `it()`、1 个显式 timeout** —— 而那 1 个，正是当初**痛过的那一条**
（12 次 spawn、9.6s，撞了 5s 默认才被单独加上）。

措辞要准，因为准了这条才立得住（#363 review 更正：我初稿写「0 个」，与我自己下一行点名的那条矛盾）：
**不是没做，是只在痛过的那一条上做了局部止痛；把它一般化写进文档之后，没有回头覆盖同类。**
剩下 13 条里最慢的用掉 5s 默认预算的 64%，而第一条付 `npx tsx` 冷启动 ——
本地 892ms，CI 上 6607ms，**7.4 倍**。它就是后来在 CI 上真红的那一条。

这是 FU-43 的**镜像**。FU-43 说的是「已交付却没标」；这一条是「已标却没交付」，
而且更难抓，因为**账本上它看起来是最规矩的那种关闭**：有 `done=PR#N`，那个 PR 真的改了东西，
改的内容也真的和这条 followup 有关。

- **一条 followup 的正文若同时含「认识」和「动作」，`done` 之前逐项点名它们各自落在哪。**
  只落了认识那半 → 要么拆成两条，要么不许标 done。
- **判据要能机械算**：FU-30 的动作那半是可数的（`grep -cE "^\s*it\(" vs 显式 timeout 数），
  而没有人去数。**能数的东西不去数，就是在用印象结账。**

## 1.5 会写树的命令，不能拿来回答只读问题

（FU-53 / FU-54 / FU-57 / FU-58 —— 2026-09-05 一天内撞了四次，三次是同一形状）

- **撤销的目标必须是动作前抓下的显式 sha**，不用 `HEAD~1`/`HEAD^`。相对 ref 的含义取决于
  「那个动作是否真的发生了」，而那正是你还没验证的事。（实例：撤一个**没有成功**的临时提交，
  `HEAD~1` 指向的是上一个真 commit。）
- **规则对任何会重写工作树的命令都成立**，不只是「撤销」：`checkout -- ` / `reset --hard` /
  `restore` 之前先 `git status --short`，有未提交内容先 commit 或 stash。
  三次的共同形状不是「撤销」，是**一条会用已知状态覆盖工作树的命令，在树里还有未提交内容时
  被执行**，而执行者当时想的是「确认状态」不是「丢弃改动」。
  > **别拿一个会写树的命令去回答一个只读问题。** 想知道自己在哪个 commit，用 `git rev-parse HEAD`。
- **commit message 一律走 `git commit -F -` + 单引号 heredoc**，永不用 `-m` 写含反引号或 `$()`
  的正文。实例：一条 message 里的反引号**真的被 shell 执行了**，而它包着 `git reset --hard` ——
  只因内层命令失败、`&&` 短路才没跑。**那是运气，不是设计。**
- **证据类文档里带 `…` 的地址一律不可复制。** 补全省略号不像「编造」，感觉像「把缩写展开」，
  所以不触发任何自我怀疑；而结果是一个**语法合法的地址**，链上会老实回答它，
  **那个答案会被当成关于原地址的事实**。若某地址来自散文，先 `cast code` 确认非空再用它下结论
  （而那条判据本身也要正对照 —— 见 §1 关于对照一起瞎掉的那条）。

## 2. 沉默不是通过

- **门禁必须先证明它看见了东西，再报告它没看见问题。** 输出里要有「解析了 N 条 / 扫了 N 个文件」，
  否则「一切正常」和「什么都没解析到」在输出上无法区分（#351、#354）。
- **空集有三种成因**：真的没有 / 谓词写错了 / 看错了地方。正对照只能排除第二种。
- **`undefined` 的 lookup 同样有三种成因**，而 `undefined` 一种都区分不了（#342：我把
  「猜错了键名」读成了「这个键不存在」）。
- **`diff` 说相同、零命中、空输出，是同一种读数的四张脸。**
- **「运行中」和「通过了」在几乎每一种朴素渲染下长得一模一样**（FU-59，#369 合并前）。一条运行中的 check 其 `conclusion` 是 `null`，而 null 的每一种自然写法都读成无害：空串、字面量 `"null"`、以及**对空串不生效的 `// "PENDING"` 兜底**。判据：**读 `status` 不读 `conclusion`**（`completed` 是唯一表示「跑完了」的值），**并且先数总条数** —— 零条 check 与零条失败在「没发现失败」这个读数上完全相同，含义却相反。
  > 实例：我写的 monitor 用 `(.conclusion//"PENDING")`，在两条 check 仍 `in_progress` 时打印了 `RESULT=GREEN`。**坏掉的量具是我五分钟前为了防这件事而写的那一个。**
- **一个指向已删除路径的配置，会静默关掉它所配置的那整套机制**（FU-3，#363 实测）。
  临时仓两组对照：`core.hooksPath` 指向存在的目录且 `pre-commit` 返回 1 → hook 跑了、commit 被拦；
  **指向不存在的目录 → 无任何输出、commit 成功。** git 不认为这是错误。
  所以「配置写着 X」不等于「X 在跑」——**要问的是「X 上次真的拦下过什么吗」，不是「配置对不对」。**
  推论：`--unset` 也未必等于「恢复保护」，它只等于「不再撒谎」——
  本仓 `.git/hooks/` 非 sample 文件数为 0，unset 后依旧一个 hook 都不跑。
  **把「让配置说真话」和「让机制生效」当成两件事，它们需要的决策层级不同。**

### 负对照通过了也可能是坏的 —— 如果它和正例坏在同一处

（FU-61，#372 评审自陈）核一个哈希时用了合约上不存在的 getter，取值失败 → 变量成错误串 →
abi-encode 失败 → 「本地重算」实际是 `keccak(空串)`。**而负对照（换一个 chainId）给出了同一个值** ——
它不是没跑，是**和正例共用那个空输入，一起瞎了**。

所以判据要前推一步：**先确认量具能产出不同的读数，再去看两个读数相不相等。**

> **「同值」在两个输入本应不同的对照里，首先是量具故障的信号，不是结论。**

与「绿不算数除非它能红」是同一族，但那条管**断言**，这条管**对照本身**：一个对照如果和被测者
共享同一个坏输入，它的绿和红都不携带信息。

### 「全 ❌」是一个有三条走法的假发现，而三条走法产生的读数完全一样

2026-09-05 一天之内，同一个「所有 selector 都不在字节码里」的读数被三种不同的错误制造出来：

| 走法 | 实例 |
|---|---|
| **探错了地址** | 探的是 45 字节 EIP-1167 代理 —— 它的字节码里一个 selector 都没有，连真实存在的函数也查不到 |
| **解错了字节** | 只匹 `363d3d373d3d3d363d73` 前缀解代理：非 1167 合约也会被切出 20 字节当「实现地址」，而那个垃圾地址 `getCode` 返回 `0x` |
| **对照的签名是猜的** | 照名字拼 `lockStakeWithTicket(address,uint256)` → 4/4 全 ❌；从 ABI 文件取真签名（**5 参**）→ 立刻 3 ✅ |

前两条是我犯的，第三条是评审在复核我的结论时犯的 —— **他复核的结论是对的，而他第一次的复核方法会得出相反答案。**

**第四条走法，加正对照抓不住它。** 评审自陈：grep 到第一个 `blsAggregator` 用了 **chain 10 的地址去问 Sepolia RPC**，拿到 3.2.1 和一个看起来完全正常的返回。

前三条的产物是**全 ❌**，形状本身就可疑；第四条的产物是**一个正常的、内容错误的答案**。结构性区别他说得很准：

> 前三条是「探测坏了」，第四条是「**探测好好的，只是问了另一个对象**」——
> **前三条能靠加正对照发现，第四条加多少正对照都发现不了。**
> （他那次若用 `owner()` 做对照，在 chain 10 上照样 ✅。）

唯一能抓住它的是**把 chainId / RPC / 地址三样一起打出来比对**。

这和 `guardianSlashCases`（同 selector 不同返回，7 参解 8 字不 revert）是同一件事的两个层面：
**一个是「问错了合约」，一个是「用错了 ABI」，共同点是链会礼貌地给你一个可信的错答案。**

### 把「我们 ABI 的命中率」报成了「那个合约有多少函数」

上一版这里写着「OP 的实现 10029 B / **27 个 function**，Sepolia 9061 B / **29 个** —— 字节更多，
函数更少」，并由此得出「体积不是版本代理」。**那个反差不存在，因为 27 不是 OP 的函数数。**

27 是**我们那份 29 条 ABI 里，有多少条在 OP 的字节码上命中**。它是一个关于**我们的 ABI**
的读数，被我写成了关于**那个合约**的读数。实测反证：OP 上有 `setRegistry(address)`，
而我们的 ABI 里**根本没有这个函数** —— 所以 OP 不是 Sepolia 的子集，两者只是**不同**。

**这是同一个错误今天的第三种形态**：

| 形态 | 实例 |
|---|---|
| 分母太窄 | 在一条链上验过，写成 SDK 的性质（FU-79） |
| 分母太宽 | 量了 16 个 import，把结论安在 19 个 mention 上 |
| **分母是另一个东西** | 量的是「我们 ABI 的覆盖」，报的是「合约的函数数」 |

判据：**每个数字都要能回答「这是关于谁的读数」。** 「27」在两个句子里都语法通顺，
而它们说的是两个不同的总体。

（顺带：不要用 PUSH4 常量个数去数函数。而**这句话里我自己那两个数也是错的**，
值得连过程一起留着 —— 它是本节论点的现场演示。）

我当时用的是朴素 regex，把字节码里每一处 `63xxxxxxxx` 都当成 PUSH4。

**读数对象**（上一版这张表一个地址、一个块高都没有 —— 违反了它上一节刚立的规矩，
#385 评审指出。**一张关于「每个数字要能回答这是关于谁的读数」的表，自己答不出来。**）：

| chain | 合约 | 地址 | runtime 字节 | 量于区块 |
|---|---|---|---|---|
| OP Mainnet (10) | `GTokenStaking` | `0x7A1216C2d814D2389698C64eD23AA1aA9Eb6343E` | 10029 | 156515050 |
| Sepolia (11155111) | `GTokenStaking` | `0x472297B557c1d0F030f281a5Bb8A535f6c5AB65e` | 9061 | 11641750 |

| chain | 半字节扫 | 字节扫 | 走查·总 | 走查·去重 |
|---|---|---|---|---|
| OP Mainnet | 43 | 35 | **29** | **29** |
| Sepolia | 65 | 58 | **56** | **50** |

**三件事，一件比一件重要：**

**一、我上一版那张表把两个统计量混在了一列**：OP 的 29 是**总数**，Sepolia 的 50 是**去重数**。
**之所以看不出来，只因 OP 恰好零重复**（29 = 29）。#383 评审量出来的。

> **一个巧合的相等，会把两个不同的统计量伪装成同一列。**

**二、我说「差额是被当成指令读的立即数」对 Sepolia 是错的。** 那里有两个不同的差额：
65→56 是立即数误读（9），56→50 是**重复常量**（6）。我引的那个 6 属于后者。
两条链上「6」这个数值出现过，成因却不同 —— **同一个数字在两个位置上讲的是两件事。**

**三、我对朴素列的整段说法是错的 —— 前提和归因都错，而真相比我写的强。**

上一版写：「朴素列在两个人的实现之间根本对不上，我量到 43/65、评审量到 35/58，
两条正则对『重叠匹配』『从哪个偏移起扫』的处理不同」，并由此得出

> ~~一个连两个实现都复现不出同一个值的量具，它给出的任何数都不该进结论。~~

**三处都不成立，逐条实测（同上表的地址与块高）：**

**① 前提被证伪：复现出来了。** 我独立写的按字节扫描给出 **OP 35 / Sepolia 58** ——
和评审的实现逐字相同。两个实现从来没有对不上过。

**② 我归的因不存在。** 「重叠 / 非重叠」这个自由度，**四个数一个都不变**：

```
OP    byte: overlap=35 nonoverlap=35    nibble: overlap=43 nonoverlap=43
SEP   byte: overlap=58 nonoverlap=58    nibble: overlap=65 nonoverlap=65
```

**③ 真因是另一回事，而且更严重。** 我的正则匹在**十六进制字符串**上，
所以 `63` 可以从**奇数半字节位**开始命中 —— 跨在两个真实字节中间。
按这个口径扫，两条链**精确复现 43 / 65**。

> **朴素列不是走查列的粗糙近似。它在读根本不存在的操作数。**
> 一个从半字节偏移上切出来的「PUSH4」不是一条指令，它是两条相邻指令的碎片拼起来的。

这个说法比我原来那句强，因为它**同时解释了为什么走查列三方一致**
（我、评审的 opcode 走查、`cast disassemble | grep -c PUSH4`）：**那三方读的都是真指令。**
原来那句只说了「量具不可复现」，而量具其实是可复现的 —— 可复现地读着不存在的东西。

判据：**「两个实现对不上」这个诊断，要先证明它们真的对不上。**
我没有跑评审的口径就断言了差异，而那个差异是我自己的口径造出来的。

**撤回一条我对评审的指控。** 我上一版写「他只复核了 OP，把 Sepolia 的 56 放行了」。
他核后指出按字面不成立：`56` 作为**出现次数**精确正确（走查总数 56，`cast` 独立也给 56）。

**而他自陈的失误更强、也更值得记**：#383 那轮他 **56 和 50 两个都报了、都算对了，
却没问那句话要的是哪一个**。

> **漏掉的不是一次复算，是没问「这个数在回答哪个问题」。**

而 OP 那侧两数恰好相等（29/29），**所以这个问题在那一侧根本不会显形** ——
与上面第一条是同一个巧合造成的两种后果。

而即使走查版的 56/29 也**不是函数数** —— 它是「代码里出现过多少个 4 字节常量」，
去重版 50/29 是「有多少个不同的 4 字节常量」。**两者都不回答「这个合约有多少个函数」。**

判据：

- 解代理要**前缀 + 后缀 + 总长三项齐验**，并配一个已知非代理合约作负对照；
- **正对照的输入必须来自独立记录**（ABI 文件、部署产物、上游源码），不能来自「我按名字拼的」；
- 尽量再找一条**互不依赖的路径**佐证（本例：解出的实现地址与 `addresses.ts` 的 `paymasterV4Impl` 逐字相同 —— 一条来自链上字节码，一条来自地址簿）。

与「负对照和正例坏在同一处」同族，但更前一步：那条说对照**共享**了坏输入，这条说对照**自己的输入是编的**。

### 每组探针必须指定一格，它的绿本身就证明量具在工作

（#350 review）恒绿的基线什么也不证明。承重的不是「基线跑了」，而是
**「基线本该有输出/有内容，而它没有」** —— 今晚四次救场全是这一格。

## 3. 测的是哪一份？它真的变了吗？

- **一棵没重新 build 的树上跑的全仓测试，红和绿都不携带信息**（FU-62，RC 后全量回归实测）。
  `pnpm -r test` 报 `@aastar/airaccount` **17 red**（`newDvtIdentitySeen is not a function`）；
  `pnpm -r build` 之后同一棵树 **17 → 0**。真因是新导出没进 dist。
  **CI 结构上看不见这一类**——它每次都从干净 checkout 全新构建。
  两个方向都成立：假红让人去查一个不存在的回归；**假绿更坏**——删掉一个导出而 dist 里还留着旧的，
  测试照样通过。判据：**跑 `pnpm -r test` 之前先 `pnpm -r build`**；任何跨包导出改动之后，
  「本机测试绿」在重建前不构成证据。
- 同族：读到 `Tests 7 passed` 而 `Test Files 6 failed` —— **6 个文件根本没加载**，
  只看 `Tests` 那行会拿一个「测试从未执行」的绿去 APPROVE（#367 评审自陈）。
  两者共同点：**测试报告的形状完全正常，而被测对象根本不是你以为的那份代码。**


每次测量前回答两个问题，**两个都是读数，不是信念**（#354 review）：

1. **测的是哪一份**
   - 新建 worktree 未 `pnpm -r build` → 测试以「N 个文件 FAIL、0 test」的形态红（#343）
   - 分离 worktree 跑的是 **HEAD 上的旧副本**，不是未提交的修复（#354）
   - `pnpm --filter` 跑的是**已构建的 dist**，stash 源码不会回滚它（#348）
2. **被测的东西真的变了吗** —— 见第 1 节末。

**一个在环境 A 下会提前 `return` 的工具，在 A 和 B 下是两个不同的被测对象**（#355：
本地有 baseline 所以走完全程，CI 没有所以提前退出 —— 两边跑的根本不是同一段代码）。

### 证据在仓库历史里的测试不是自洽的 —— runner 的 checkout 方式是它 fixture 的一部分

#379：一条测试断言门禁对 `9e538e07`（合并 #377 却没记 T1.2.3 的那个 commit）会红。
CI 的 `actions/checkout` 默认 `fetch-depth: 1`，那个对象不存在，`git show` 抛异常，
**承载全部论点的两条（历史红 + 它的正对照）一条都没跑**。
本地测不出来，因为本地有完整历史；评审用 `--depth=1` 才复现出与 CI 逐字相同的失败。

三条判据：

1. **钉死 SHA，不用分支名。** #380 里我读的是 `git show origin/main:…` —— 一个会移动的 ref。
   那个 PR 一合，`origin/main` 就不再携带烂掉的那份文件，用例会转而断言「最近落地的是什么」。
   **fixture 是移动引用的测试，测的不是历史，是「最近」。**
2. **确认执行环境真的拿得到那个对象**（CI 默认浅 checkout）。
3. **在浅 checkout 下跑一次，确认它是红而不是静默跳过。**

第 3 条是成本所在，也是最该警惕的一格：这次 `git show` 抛异常、vitest 报失败，**还算响**。
若当时写了 `try/catch` 兜底，它就会变成静默跳过 —— **而「加个兜底让测试更健壮」
恰恰是很自然的一步**。把「拿不到证据」写成「跳过」，等于把一条论证删掉而不留痕迹。

另一条路是把旧文件复制进仓库当 fixture。那样是自洽的，
**同时也是一份不再能证明「当初发生过什么」的副本** —— 取舍要写下来，不要默认。

## 4. 人工恢复步骤是没有守卫的一格

（#352 review 命名）撤变异、解冲突、超时后手动清理 —— 共同点是：
**机器刚刚响过一次，而人正是被那声响召唤来做判断的；于是这一步天然没有守卫，
因为「已经有东西响过了」本身让人觉得它被看管着。**

- `git checkout -- <file>` 撤变异会连**同一文件里的修复**一起撤，而测试仍全绿（FU-33，#344）。
  判据：被变异文件的 `git diff` 与 `git diff --cached` 都为空，**且修复的标记字符串仍在**。
- **被超时杀掉的命令会把变异留在树上**（FU-36，#346）。注入与还原不要放在同一条可能超时的
  命令里；**还原必须是独立的一次调用**，否则「变异跑完了」和「还原做完了」共用一个成败。
- 解冲突时按 id 去重、保留先出现的那条，会丢掉自己那半（#352）。
  判据：**「本分支 vs main 的差异应当非空」** —— 差异为空就是信号。

## 5. 门禁的形状

### 一道门禁的**扫描单位**就是它的能力边界，要写下来而不是让人去猜

（FU-29，#339 review）`scripts/security-scan.ts` **逐行**扫描，所以它的「这是公开数据」否决
只能看这一行。它防的是「同一行里把秘密说成公开」，防不了跨行上下文：

```
private key (do not commit):        ← 秘密在上一行
pubkey = 0x…                        ← 公开标记在下一行 → 够不着
```

两点要一起记，否则这条会被误读：

- **这不是 #339 引入的**，逐行是这个脚本一直的形态。把它写下来不是记一个缺陷，是记一条边界 ——
  **一条没被写下来的边界，会在下一个人「这个不是有门禁吗」的时候变成一个假保证。**
- **实测边界比原先担心的窄**：评审试过 `| pk | \`0x…\` |` 这种表格列形式，**是被抓的**。
  所以不要凭「逐行」这个词去推它漏什么 —— 要跑一遍。

### 相等会被删掉，下限不会

`= 37` 在**新增**时也红 → 逼人频繁改它 → **而频繁改的数字就是不动脑子改的数字**。
下限只在**变少**时红：新增自由，减少必须显式编辑，**而那次编辑正是有人问「为什么少了一个」的地方**（#355）。
同形：`min` / `maxGated`（#352）、`MIN_SDK_PATHS`（#355）、不透明白名单条目上限（#359）。

### 关系对整体缩水免疫

`B ⊆ A`、`A ⊆ C` 都是**关系**，数据整体少一条时它们一起滑过去，一条不破（#355 review）。
**只有外部基准能发现「少了一个」。**

### 一个报出两打非问题的门禁会在抓到第一个真问题之前被删掉

（#354、#357）规则的宽窄**不可能在写规则时想清楚** ——
**「在真数据上跑一次」不是验收步骤，是设计步骤。**

### 过严的守卫真正的失败方式

不是误判，是**被关掉**。所以「编号断层」不报警（#351）、可核实的新增不计入上限（#359）、
叙述性引用不算关闭主张（#357）。

### 一个看起来更强的门禁，比一个诚实的弱门禁更危险

缺口要写成**明确断言不覆盖的用例**，而不是删掉 —— **一条声明缺口的测试，是这个缺口将来被人看见的唯一途径**（#357 review）。

### 门禁报出来的数，必须和它核过的数是同一次计算

不是「两次今天恰好一致的计算」。`check-followup-closure` 曾把「本 PR 声称关闭哪些」算了两遍——
判定那份过了引用过滤，打印摘要那份没过。于是输出成了：

```
of those, 1 are CLAIMED closed by this PR: FU-65      ← 未过滤
✅ every follow-up this PR CLAIMS to close is closed   ← 过滤后 = 0
```

**两行上下紧挨着，读者会把 ✅ 读成对上面那个 1 的裁决。它是对空集的裁决。**

这比「零条声称也打绿」更坏：后者读者至少能看出什么都没查，前者的摘要**主动提供了一个裁决
从未拥有过的主语**。同一文件里的两份定义会静默漂移，因为没有任何东西在比对它们——这正是
本仓 task-ledger 对「两份手写账本不能互校」讲过的道理，只是这次两份定义在同一个文件里。

### 门禁的作用域由它能解析什么定义，于是它对解析不了的行永远报成功

而**漂掉的行不成比例地就是那些解析不了的行，因为没有任何东西在把它们拉回来。**

实例：`tasks.md` 里 `T1.1.2` / `T2.1.1` 长期标 `PR_OPEN`，而它们的 PR 早已合并。
`check-task-ledger` 只能对**含 PR 号**的行产生 claim，这两行都不含（其中一行正文里那个 `#362`
是裸 `#`，正则要的是 `PR #N`），于是零条 claim → 打印 `✅ every PR claim agrees with GitHub`。
那句话是真的，只是它说的是空集。

**修法不是让门禁去猜，是让它检查「这个问题问不问得出来」**：状态若断言一个在飞的 PR，
标题里必须点名那个 PR。它不核状态对不对（有了号自然能核），它核的是可核性本身。

### 我一天之内做坏了三次量具，全都在「数失败条数」这一步

`tail` 吞掉退出码（`cmd | tail` 的 `$?` 是 tail 的）、`(.conclusion//"PENDING")` 对空串不生效、
`grep -oE 'Tests +[0-9]+ failed'` 匹配不到（vitest 在 `Tests` 和数字之间插 ANSI 转义）。

三次的共同形状：**读数经过了一层我没在看的转换。** 第三次尤其值得记——它让五条变异全部显示
`0 failed`，如果就此收手，结论会是「这些测试一条都不管用」，而真相恰恰相反。

判据：**量具本身要先过一次正对照**——先让它面对一个已知失败的输入，确认它能说出「失败」。

## 6. 断言钉的是什么

| 写法 | 钉的是 | 移除行为时 |
|---|---|---|
| `@ts-expect-error` | **编译器的行为** | 会红（TS2578） |
| `expect(source).toContain("…")` | **文件里的字符** | **不会** —— 字符可以留在注释里 |

**源码文本断言只在「这个性质本身就是文本层的」时承重**（例：禁 `stdio: ['ignore','pipe','ignore']`
这种写法 —— 它丢掉的信息在源码里可见、在任何一次健康运行里都不可见）。
**一旦要钉的是「运行时会发生什么」，文本断言就只是一句写在测试里的注释**（#354）。

**可执行的处方**（#359 review）：

> **凡是「禁止某个东西存在」的断言，先问它数的是「出现」还是「生效」。**
> 「不许出现字符串 S」在一份会讨论 S 的代码库里**必然**误报；
> **「S 不许被解析 / 被调用 / 被求值」才是那个性质。**

上面那张表说明了**为什么**文本断言不承重；这一句才说了**下次该怎么写**。

今晚在同一个陷阱上栽了两次，**两次都发生在写「解释为什么不做某事」的时候** ——
那段解释文字本身含有被禁的字符串（#354、#359）。**你越认真解释为什么不做 X，
你的文本就越像做了 X。**

### 测试喂进去的值，下游会不会接受

`"0xn1"` 这种假 nodeId **本仓库任何编码器都不接受** —— 用它喂出来的测试，对
「形状检查被加上或去掉」这一整类变化**天然免疫**（#343、#348）。
**一个用系统拒绝的输入喂出来的绿，和一个没被执行的绿，信息量一样是零。**

而 fixture 要**为区别而造，不是为真实性而造**：真实端点 `https://dvt1.example` 没有路径，
所以「host」和「全 URL」是同一个字符串，变异不会红（#357）。

## 7. 规则设计

### 找到正确的坐标之后，还要问：我用来测它的东西，和这个坐标是同一件事吗

（#357 review）「谁在主张」的直接证据是**引用语法**；「这行提没提别的 PR 号」是一个
**相关但不同**的量。**相关量在大多数样本上给出正确答案 —— 这正是它难被发现的原因。**

可执行形式：**收窄一条规则时，要拿「新坐标为真而旧代理为假」和「新坐标为假而旧代理为真」
的输入各测一次。**

而这两类不会同时找上门：**收窄的动机几乎总是「它报了不该报的」——误报把你叫来，
所以你手上天然只有后者的样本；前者（被新规则误杀的真主张）没有人会来报告它，
它的表现形式是沉默**（#357 review）。

### 「用 X 替掉 Y」时，先列出 Y 抓到过的每一类

（#355 review）**不要问「X 好不好」。** 而且**别按「我记得的 bug」列，按 Y 的每一个失败出口列** ——
`= 37` 只有一个出口（不等），而不等有两个方向：**多了、少了**。
**方向是可枚举的，记忆不是。**

「替换」这个词自带只增不减的暗示，**而它恰恰是最容易减的一种改动形状**。

### 先问矛盾，再问权衡

（#358 review）「这条建议和这个东西存在的理由冲突吗」比「权衡起来划不划算」**更容易判断**
（只需读那个字段的用途声明），而且 **权衡可被新论据推翻，矛盾不能**。

例：pin 的用途是 *discovery-free default*，**让它动态读链就是让它需要发现过程 —— 那不是改进它，是取消它。**

## 8. 报告与归因

- **一个够不到权威源的检查什么都没核实，不能说它核实了。** 调用失败 ≠ 「没有」——
  只有权威源自己说的「不存在」才算不存在（#354：一次 `gh` 瞬时失败被报成「PR #339 不存在」，
  而它一小时前刚合并）。
- **沉默要人去发现「什么都没发生」，而一句指名道姓的诊断会被人拿去行动** ——
  「#339 不存在」的下一步是有人去改那个号，**量具的故障会被写进账本，从此看起来像事实**。
- **一条指名了没人能执行的动作的错误信息，比一条什么都不指名的更糟** ——
  它让运维去找一个函数，而不是去找一个人（#347：`snapshotEpoch()` 不在部署字节码里）。
- **处方在给出之前，先要确认它指的东西存在**（#347 review）。

### 两个正确的测量给出不同的数

第一反应不该是「谁错了」，是 **「我们各自在数什么」**。
**谁先去算「谁错了」，谁就会开始为一个不存在的错误找解释** ——
而「谁错了」是更短的问题、有一半概率立刻结束对话，**所以在时间压力下总是先被问出口**（#359）。

## 8.1 错误的可见性和它的代价成反比 —— 所以直觉会先去核最不需要核的那条

（FU-46，#361 review）`AirAccount/kms/node-setup/setup-server.py` 硬 pin 了三个 Sepolia 地址：

| pin 的键 | 对不对 | 填错了会怎样 |
|---|---|---|
| `gToken` | ✅ 逐字等于 canonical | 当场 revert |
| `staking` | ✅ 逐字等于 canonical | 当场 revert |
| `validator` | ❌ 是**已被取代**的那个 | **一路成功** |

三条里错的只有第三条 —— 而它恰恰是**唯一一条填错了不会有任何东西提醒你**的。
新旧两个 validator 都有代码、都对我们的节点答 `isRegistered = true`，
所以「有代码」和「认得我们的节点」这两个最顺手的检验，一个都区分不出来。

这不是巧合，是结构：**一个错误越容易被下游自动发现，就越不需要门禁；
越不容易被发现，就越只能靠门禁。而人的注意力分配恰好相反** ——
`gToken` 是否正确容易核，所以先被核；`validator` 是否是活的那个难核，所以被跳过。

- **列出一组值时，先按「填错了多久会被发现」排序，从最慢的那一头开始设检验。**
- 同族读物：第 1 节「链上此刻造不出这个区别」（FU-30 红也要归因）、
  `packages/core/src/dvt.onchain.test.ts`（两个 validator 答得一样，所以检验必须从 router 起）。

## 9. 一道门禁最坏的失败方式，不是漏掉错误，是把人推向错误

（#360 review）`check-followup-closure` 要求账本说真话，而它对「补记账 PR」的**第一条处方**
（把 `done=` 指向本 PR）**会让账本声称一个只改了一行 markdown 的 PR 交付了那份实现**。

判据：**给出处方之前，把处方本身当成一次改动，问它会写下什么。**

## 9.1 一条规则风险最高的一次应用，是引入它的那个 PR

（#360 review）今晚四个数据点，四个不同的时刻，同一个位置：

| | |
|---|---|
| #354 | 写「必须用行为断言」的那个 PR，自己用了文本断言 |
| #359 | 写「不许有 `--file`」的那段解释，自己触发了那条断言 |
| #360 | 写「PR 必须诚实关闭 followup」的那道门禁，红在自己身上 |
| 评审 | 写「在真数据上跑一次是设计步骤」的那条 review，自己没在那条 PR 上跑 |

外加一个第五点：**我声称把一条处方「原样收进第 6 节」，而它根本不在文档里** ——
一句关于本文档内容的主张，没被检验过，被一条 grep 推翻（#360 review）。

所以不是「要更小心」。那次应用**没有先例、没有别人踩过的坑可查，而作者正处在
「解释它」的模式里，不在「执行它」的模式里**。

> **引入一条判据的 PR，必须把这条判据先用在它自己身上，并把那次运行的读数贴出来。**

它和第 9 节同族：**两者都是关于门禁自身、而不是关于被测代码的失效。**

## 9.2 便利包装不是机械强制层

`git-guard merge-pr` 核审批、核分支保护，**不核 CI 结论** —— 而 2026-09-05 实测，`main` 的
`required_status_checks` **未启用**：所以「CI 红也能合」在**服务端本来就是被允许的**，
本地脚本只是没补这一课（FU-41，#349 那次事故）。

判据：**问一道防线「它在哪一层」**。
本地脚本是便利包装，可以被忘记、被绕过、被 `--force` 掉；
服务端的 required checks 是机械层，**不依赖任何人的记性**。
一道只存在于便利层的规则，等于一条写在注释里的规则。

## 10. 关于跟进项本身

- **一条 followup 如果经得起被证伪一次还站着，剩下的那半通常才是真的那半。**
  机制：最初的措辞里混着「一个真的结构性问题」和「作者当时对它的错误解释」，
  证伪只打掉后者 —— **因为解释可检查，结构是被观察到的**（#358 review）。
  可执行：**一条从未被证伪过的 followup，值得主动去试着证伪一次。**
- **可推迟的步骤在长夜里一定会被推迟。** FU-31 / FU-37 / FU-34 三条「已交付却没标」，
  成因各不相同，但**三次都存在一个「本该在这里做、但可以推迟」的时刻**（#360）。
- **把「靠记得」换成「不做就红」，哪怕只覆盖一部分**（#357）。

## 一个 8% 占空比的 fail-closed 窗口 —— 以及为什么轮询量具看不见它

CC-115 B6 期间，三个 committee 证据 runner 同时全红，`requiredQuorum()` 返回
`type(uint256).max`。第一反应是「我刚才改坏了」。链上一读，几十秒后它自己好了。

成因：`epochLength = 64`（Sepolia ≈ 12.8 分钟）。**epoch 翻页之后、keeper 调
`snapshotEpoch()` 之前，`_epochUsable(e)` 为假，整个 committee 路径 fail-closed。**

量化（pr-daemon 独立测的，用的是**历史区块探针**）：

```
epoch 181901 起始区块 = 181901 × 64 = 11641664
  11641664..11641667   pinned=false   requiredQuorum = 2^256-1
  11641669             pinned=true    requiredQuorum = 3
```

**每个 epoch 前 ~5 个区块 fail-closed，占空比 ≈ 5/64 ≈ 8%。**
一个在随机时刻启动的 runner，**约 1/13 会撞进这个窗口。**

### 三条读数，每条都改变了我们之前说过的一句话

**① 「链上健康态下 e2e 走不到哨兵分支」是错的。** 三方（我、评审、DVT）都这么认为过：
DVT 据此说它未被覆盖、我据此说有单测就够、评审据此接受。
**它每 12.8 分钟触发一次。** 那不是罕见分支，是一个可预测的周期性状态。

**② 「这个环境造不出那个输入」这句话必须带两个限定词。**
我原本只想到一个（**在多长的观察窗口内**）。评审补了第二个：**用哪个量具**。
他先用状态轮询采样 40 次、约 1 分钟，**全部落在 pinned=true 里，什么都没抓到**；
换成历史区块探针，**立刻**抓到。同一个环境、同一时刻，一个量具交出空集，
另一个交出读数 —— 而**空集当时被读成了"造不出"**。下面一格算的就是这个误读。

> 完整形式：**「在 ⟨多长的观察窗口⟩ 内、用 ⟨哪个量具⟩，这个环境造不出那个输入。」**

**这次落空的是哪个限定词 —— 我第一版答错了，而答错的方式值得留着。**

第一版写的是「量具不匹配：等多久都没有」。**它与本文上面自己的读数直接冲突。**
按 `epochLength=64`、窗口约 5 个区块算：状态寿命 ≈ 1 分钟，周期 ≈ 12.8 分钟；
那次轮询 40 次约 1 分钟，采样间隔 ≈ 1.5 秒。**1.5 秒的间隔远小于 1 分钟的寿命** ——
轮询只要跨过下一次 epoch 翻页，就会连拿几十个样本。跑一整天会命中约 110 次，
不是「一次也不」。

所以真正落空的是**第一个**限定词：

| 限定词失效 | 本例 | 补救 |
|---|---|---|
| **窗口不够长** | **✅ 就是这一条**：观察窗口 1 分钟 < 事件周期 12.8 分钟 | 等更久（或读历史，见下） |
| 量具不匹配 | ❌ 不是这一条。轮询能看见这个状态，只是那一分钟没赶上 | 换量具 |

**那历史区块探针赢在哪？不是「可能 vs 不可能」，是延迟。**
轮询要等下一次窗口到来（期望 ≈ 5.9 分钟；**最坏 11.8 分钟 = 周期 − 寿命 = 768 − 60 秒**，
不是整个周期 —— 最坏情况是「刚错过」，不是「刚开始等」）；历史探针不等 ——
**已经发生过的窗口还在链上**，它一次读取就能取到。换量具在这里买到的是时间，
不是能力。把它说成能力差异，就把一个「多等六分钟」的问题说成了一堵墙。

**但「历史不会溜走」本身带一个前提，而这个前提又是一次「用哪个量具」。**
历史状态读是 `eth_call` 带 `blockNumber`，**非归档节点通常只保留最近约 128 个区块的状态**。
那次探针跑通了，说明当时那个端点能服务那个区块；换一个端点，同一条读取会以
「missing trie node」之类的形式失败 —— 而那种失败**不长得像空集**，是会报错的，
所以它至少不会被误读成「不存在」。（本仓配置的端点我没测过，这里只记前提，不下判断。）

> **一次落空的采样，本身不能区分「窗口没覆盖」和「量具看不见」。**
> 要分开它们，得先算一遍事件的**寿命**与**周期**，再和观察窗口比 —— 那是算术，不是判断。

（本条的更正由评审给出：初稿把这次落空归因给量具，而本文自己上面几行的读数就否证了它。
一条与同一页上的测量矛盾的归因，比没有归因更糟，因为它读起来像已经量过。）

**③ 保守拒绝和真实不一致，在错误消息里必须分开。**
根比对（`runningRoot` vs `epochSetRoot[e-1]`）对这两种状态给出同一句话，
而它们完全不同：翻页窗口一分钟内自愈、占 8% 的时间；集合真变动持续到本 epoch 结束
——**而且即便如此，针对 `[e-1]` 的 proof 依然有效**，因为这个闸门本身是保守的。

把两者混在一句消息里，会以可观频率产生"不是真问题"的红。
**把红训练成噪声**正是本仓反复在打的那个模式，所以
`describeFrozenRootDisagreement` 把它们分成两句，翻页那句直接说
「Retry rather than investigate」。

### 量具和问题不匹配 —— 同一天的第三例

| 谁 | 问题 | 用的量具 | 结果 |
|---|---|---|---|
| 我 | 「还有谁在调这个函数」（关于**完整性**） | `grep \| head` | 截断，漏掉两个 runner |
| 评审 | 「这个名字在数组里几次」（关于**数组范围**） | `grep -c`（**文件**范围） | 差点报出一个假发现 |
| 评审 | 「这个窗口存在吗」（关于**稀有事件**） | 状态轮询 40 次 | 空集 |

三个都不是粗心。**都是拿一个会截断/换范围/采样不到的工具，去回答一个关于完整性或存在性的问题。**

## 注释在冒充证据

同一天里，变异**三次**抓到同一个形状：`0n === 0n` 的顺序断言、
`matches.length !== 1` 的第一版、`epochPinned` 的读。三次的共同点不是「变异做得不够」——

> **每一次我都在测试旁边写了一句「这条能挡住什么」的注释，然后没有去验证那句话。**

这比「变异覆盖不足」准，因为它指出了病灶：**一句写在测试旁边的能力声明，
读起来和一条被验证过的性质一模一样**，而且它会随代码一起被复制到下一处。
`0n === 0n` 那条的注释写着「位置比存在更重要」——**注释是对的，测试没有实现它**，
而读代码的人会以为它实现了。

规则：**只要写下「这条测试挡住了 X」，就必须当场跑一次让 X 发生的变异。**
写不出那个变异，说明这句话还不知道自己在说什么。

（由 pr-daemon 在 #390 复审中归纳成现在这句。）

## 复审的对象是这一版的全部声称，不是上一版的 finding 列表

（pr-daemon 在 #396 复审中自报，我据此写成判据；判据行由他给出。）

他这一轮**已经写完 APPROVE 正文**，是随后回来的独立评审把两条阻塞翻出来的。
成因不是马虎，是**复审的输入选错了**：他核的是「我上轮提的那几条收干净没有」，
而没有把这一版**新写的那句 `✅`** 当成一句需要重新证伪的新声称。

> **一次复审若只核「上一轮的清单」，就会放过这一轮新造出来的每一句话。**
> 而修复一条「声称超出所检」的 PR，恰恰是最容易新造出这种句子的地方。

**判据**：复审的清单 = 这一版 diff 里每一句新增的**声称**（注释、报告文案、
`PASS`/`✅` 行、PR 正文），每一句各自问一次「它声称的，这一版的代码建立了吗」；
上一轮的 finding 列表**只是其中一部分**。

它有一个可枚举的输入（新增的声称）和一个逐条判据 —— 而不是一句态度。
